# Apple UI Correction Playbook

Use this playbook for broad Apple-platform UI work, a surface described as non-native, overbuilt, visually noisy, insufficiently minimal, or inconsistent, and for bugs where a local modifier change has not fixed the root cause.

## Evidence Order

Follow the evidence in this order. Stop guessing as soon as the current layer explains the symptom.

1. **Product state:** Name the user's current state, next action, safe escape, secondary actions, and the product invariant that must survive.
2. **Source ownership:** Find the view, shared component, state owner, modifier chain, toolbar placement, style, tint, foreground environment, and persistence boundary.
3. **Rendered output:** Compare the smallest relevant size and a representative larger size across supported appearances and state variants.
4. **Interaction behavior:** Exercise state changes, accessibility, lifecycle restoration, and cross-surface projections.
5. **Hardware behavior:** Pair with `apple-device-validation` when touch, drag, sensors, installation, or phone/watch delivery is part of the claim.

Treat summaries and screenshots as indexes into this evidence, not replacements for source and runtime inspection.

## Operational Correction Matrix

| Symptom | Inspect | Correct | Verify |
| --- | --- | --- | --- |
| The screen is plausible SwiftUI but the next action is unclear. | Current product state, primary action, safe escape, duplicate prominence, and information from adjacent steps. | Rebuild hierarchy from the live workflow. Keep one primary action and demote or relocate rare actions before styling. | Read the screen in every important state without relying on color alone; confirm the primary action and escape remain obvious. |
| A create or edit sheet looks like a dense settings model, pre-saves a placeholder object, or makes Cancel perform cleanup. | The real commit boundary, whether the draft is a value or a context-bound model, autosave behavior, keyboard submit actions, which choices are primary, downstream meaning of status labels, and every persisted object that references the item. | Keep creation in a value-type draft and insert only on explicit Create. Give the main form only the few decisions required to identify the object, move infrequent rules into one native secondary form, make keyboard submit end text entry only, name status by its true scope, and block destructive deletion when history still depends on the object. | Cancel, swipe away, force-terminate, and relaunch without leaving a placeholder record; then create, relaunch, and reopen to prove persistence. Exercise editing, duplicate validation, compact and Dynamic Type layouts, shared or published snapshots, and dependent history before claiming the workflow is safe. |
| A modal editor opens its keyboard immediately, scolds untouched fields, or offers no obvious way to unfocus. | Presentation-time focus mutation, personal-information content types, validation timing, submit behavior, blank-area and scroll dismissal, competing dismissal owners, and whether icon-only actions retain semantic labels. | Present the editor unfocused, start input only from an explicit field tap, show a field-specific error only after nonempty invalid input leaves focus, and provide an inert blank dismissal surface plus scroll dismissal. Clear focus before exit or confirmation and let one owner dismiss. Keep symbol actions local to compact editors and preserve their accessible action names. | Capture the initial editor with no keyboard or premature error, then tap each field, submit between fields, dismiss from blank space and scrolling, cancel or save while focused, and inspect VoiceOver action names. If presentation crossed Hang Detection, measure the sheet and later keyboard entry separately on the target device. |
| Repeated discrete numeric settings each open a long option page, or a first-party ruler tempts a custom imitation. | Whether the values are linear or irregular presets, current and legacy values, the public SDK declaration behind the referenced system affordance, the draft or commit boundary, and whether categorical fields are being treated as numbers merely for visual consistency. | Prefer one native wheel expanded in context for predictable discrete numeric choices, with only one wheel open at a time. Bind selection to the existing draft, keep the outer Create or Save as the only persistence action, preserve valid off-preset stored values, and leave categorical choices in categorical pickers. Do not recreate a private first-party ruler with custom physics or haptics when no public semantic control exists. | Scroll nearby and distant values, collapse and switch rows, cancel or discard, create or save, terminate and relaunch, and exercise VoiceOver, Dynamic Type, compact layouts, localization, and any valid legacy value. Verify the exact public API in the installed SDK before claiming parity with a system-app screenshot. |
| An inbox or approval queue asks the recipient to add the incoming object manually. | Who originates the object, how it is delivered, whether the visible action is a workaround, and what automatic intake is unavailable or disabled. | Preserve the real actor and state model: senders create requests and recipients review or resolve them. When the recipient initiates the outcome directly, create the resolved object without manufacturing a pending state. Keep the empty state descriptive and repair automatic intake at the service boundary. Do not retain a speculative manual importer for recovery; use retry, reconciliation, honest errors, and test-only fixtures instead. | Exercise sender submission through recipient arrival and resolution end to end, plus recipient-initiated creation and delivery failure recovery. Confirm the recipient never recreates an item another person submitted and never enters a pending state for a decision already made. |
| A deferred service dependency has created offline modes, setup switches, or manual fallbacks in the customer workflow. | The intended operational workflow, actor ownership, which dependency is merely unfinished, whether the fallback restores a failed real action, and whether operator configuration has leaked into product UI. | Treat the dependency as a release gate. Build one coherent workflow against the intended contract, keep infrastructure configuration out of customer surfaces, and remove alternate modes that exist only because the dependency is unfinished. Retain recovery only when it retries or reconciles a real attempted side effect. | Test the intended workflow with a service mock, then test transient failure and reconciliation separately. Confirm no customer action recreates service-delivered data, exposes operator credentials, or selects an implementation mode. |
| A welcome screen looks polished but feels generic, misaligned, dated, or copy-heavy. | Literal product purpose, release-truthful benefits, whether each supporting line adds an action or merely repeats the label, native title gutter, custom content inset, bottom safe-area material, progression-symbol order, and risky compact sizes. | State the job and differentiation first, then keep only a few real outcomes. Give each supporting line one compact active verb; do not replace an overlong explanation with a noun fragment that says nothing. Match the system title gutter, retain safe-area reachability without decorative tray material when separation is unnecessary, and place a direction-aware forward symbol after its label in logical reading order. | Render the exact first-run state in supported appearances and a risky small size; verify copy scanability, title/body alignment, CTA reachability, Dynamic Type, VoiceOver order, and right-to-left mirroring. |
| A privacy-policy link near the first primary action reads like mandatory agreement or disappears after onboarding. | Whether the policy is disclosure or a genuine versioned agreement, whether acceptance is recorded, which permissions or collection need separate consent, the link's visual hierarchy, the presentation semantics, and permanent post-onboarding access. | Keep a disclosure link visually secondary, open it with a native readable presentation, and do not turn `Continue` into blanket consent. Keep the current policy reachable from a permanent Settings or About surface and route privacy semantics to `apple-privacy-system-integrations`. | Verify VoiceOver order, Dynamic Type, sheet dismissal, unchanged primary-action prominence, permanent access after onboarding, and parity with the public policy. |
| First-run setup feels like a settings form, the keyboard needs custom chrome, or a permission row changes size unexpectedly. | Which fields and permissions are needed immediately, which workflow owns deferred identity or preferences, focus and submit semantics, dismissal paths, and direct `Form` or `List` child identity across states. | Keep only immediate setup, defer workflow-specific data, use native submit plus explicit focus and tap or scroll dismissal, and retain one stable row whose accessory changes in place. | Exercise idle, focused, submitted, system-prompt, denied, and granted states; compare row geometry, labels, focus dismissal, Dynamic Type, and layout diagnostics after every transition. |
| A keyboard or AutoFill candidate surface persists over the next screen or status bar after a route or root transition. | Focus ownership, `textContentType`, every submit and dismissal path, whether the focused field hierarchy is destroyed in the same update that clears focus, and any false assumption that `Task.yield()` guarantees rendering. | Clear focus, enter an explicit view-bound completion phase, keep the input hierarchy alive through an update and bounded teardown grace when needed, then transition. Remove unnecessary personal-information content types, and do not mask the defect with status-bar hiding, padding, or safe-area overlays. | Exercise Finish while input is active and rapid native-submit-to-Finish without an extra settling wait. Capture immediately on a physical device with the relevant keyboard and personal AutoFill state, then compare background/foreground and cold-relaunch controls. |
| A surface looks native but behaves or sizes like custom chrome. | Exact control type, role, style, `controlSize`, `buttonBorderShape`, placement, wrappers, gesture handlers, and accessibility actions. | Replace tappable stacks, custom press layers, or hand-built chrome with native controls and placements. Remove wrappers before adding styling back. | Exercise enabled, disabled, pressed, hover, keyboard, VoiceOver, Dynamic Type, and localization states relevant to the platform. |
| Every option in a mutually exclusive menu appears selected, or selection state drifts from the displayed value. | Menu construction, binding owner, `Picker` selection, unique tag identity and type, custom checkmarks, nested presentation, and commit side effects. | Use one native `Picker` inside the `Menu` when the values are mutually exclusive. Remove hand-managed checkmarks and keep applying a value separate from dismissing unrelated navigation. Use immediate binding for an inline menu; retain a local draft and explicit confirmation only when the chooser is intentionally staged. | Open the menu in the target runtime, confirm exactly one checkmark and no accidental submenu or duplicate value, then observe the owning row or model update at the intended commit point. |
| A custom tab bar, pill cluster, glass island, search drawer, or aspect-ratio hack is aging badly. | Whether a platform tab, toolbar, sheet, inspector, search presentation, or button shape now expresses the interaction. | Prefer the platform API. Retain custom structure only when the interaction truly differs and its accessibility, motion, geometry, and state behavior are explicitly owned. | Compare platform behavior, transitions, focus, safe areas, and size classes; use runtime proof before replacing a stable path with a new API. |
| A prominent button resolves unexpected foreground or dominates the screen. | Button role and style, tint, parent foreground, material or background, label composition, enabled state, and whether prominence is semantically justified. | Use prominence only for a true commit, save, resume, or advance action. Repair style and environment rather than forcing white or black foreground. | Check supported appearances, enabled and disabled states, contrast, and adjacent control hierarchy. |
| A product-specific filled button appears to need an explicit label color. | Whether the fill, material, role, style, parent environment, or label composition prevents SwiftUI from resolving readable foreground. | Keep native `Button` behavior and let one reusable component own the fill and shape, not the label foreground. Revise the presentation or control structure instead of forcing white, black, or another explicit label color. | Test all appearances, interaction and enabled states, Dynamic Type, increased contrast when supported, and every call site; reject component-level and per-screen foreground overrides. |
| A brief save or teardown swaps a primary button for a spinner, changes its label, or makes it jump in size. | Actual operation duration and uncertainty, whether progress helps the user decide or wait, conditional label hierarchy, symbol size, disabled state, and navigation delay. | For a short deterministic transition, keep the original label and stable geometry while disabling repeat taps. Show progress only when the wait is long or uncertain enough to need feedback, and keep that presentation within the same size contract. | Measure the button immediately before and after the tap, inspect the transient state rather than only the destination, and confirm no progress indicator or alternate label appears when the operation is intentionally silent. |
| Control geometry changes unexpectedly or communicates the wrong priority. | Explicit frames, padding, label length, symbols, state branches, hover or press modifiers, and circular-versus-capsule role. | Stabilize the component dimensions and let text wrap or scale inside them. Use shape and size to clarify role rather than decorate. | Compare localized labels, Dynamic Type sizes, state transitions, and compact layouts for movement, clipping, or false prominence. |
| A system button remains too small after changing `controlSize`. | The platform's runtime mapping for the requested size, label font or symbol scale, style, border shape, wrapper geometry, and intrinsic content size. | Keep the native `Button`, style, and shape. Increase intrinsic label size with a semantic font or symbol scale when appropriate instead of drawing or hard-framing the control. | Inspect the rendered diameter and hit target in the exact platform runtime; confirm pressed, disabled, Dynamic Type, and neighboring-toolbar behavior remain native. |
| Two halves of an action drift apart. | State owner, label, symbol, tint, enabled state, side effects, timer or sensor effects, persistence, tests, and companion projections. | Model both halves as one state machine and one reusable control: pause/resume, begin/complete, start/end, expand/collapse, or connect/disconnect. | Exercise every transition, interruption, background/foreground cycle, crash/relaunch path, and affected projection. |
| A timer, metric, or status appears to belong to the wrong object. | State ownership, visual grouping, toolbar or content placement, and details from previous or next steps. | Place live information with the state it describes. Separate process-level chrome from item-level or step-level state. | Confirm a user can identify what is running, what changes next, and which action affects it without reading adjacent detail. |
| Repeated rows, cards, search surfaces, or page chrome look almost the same. | Call sites, helper ownership, typography, formatting, state variants, search configuration, and navigation containers. | Extract the actual shared component or helper instead of tuning copies independently. Keep experiments reversible. | Sweep all call sites and compare behavior, not only pixels; restore the stable native path if a new presentation cannot be proven. |
| A flat library list shows faint lines above or below an empty or single item, or a separator begins at an absurd content-derived inset. | Whether the screen is a flat collection or a grouped form, `List` and `Section` hierarchy, section versus row separators, empty states represented as rows, list style, and automatic separator-leading alignment. | Hide section boundaries and every separator around non-item rows. Keep native row separators only between real siblings, so `n` items produce `n - 1` separators. Scope the rule to flat libraries; do not globally remove meaningful grouping from settings or detail forms, and do not draw custom dividers unless native row semantics cannot express the relationship. | Render empty, one-item, and two-item states in the simulator; confirm zero, zero, and one separator respectively, then verify rows remain single accessible actions and grouped forms retain their intended structure. |
| A watch or compact surface is crowded or truncated. | Copied phone controls, icon cost, mixed shapes, label length, action count, and whether the main screen is reserved for the current action. | Design a compact interaction model separately. Remove copy before shrinking it, remove icons before truncating, keep one obvious action, and move secondary controls to a native secondary surface. | Pair with `apple-device-validation` for small and large watch or compact destinations, plus paired-phone behavior when state crosses devices. |
| A visual complaint tempts another modifier patch. | Source hierarchy, modifier order, inherited environments, style ownership, and the screenshot state. | Remove custom layers until native behavior returns, then add only the minimum product-specific presentation at the correct owner. | Re-render the exact state and risky size; a successful build alone is insufficient evidence. |
| A new SwiftUI or Liquid Glass API appears to replace a stable implementation. | Availability, semantic contract, SDK declarations, platform guidance, existing interaction behavior, and rollback path. | Adopt only when the API matches the product interaction and removes rather than relocates custom behavior. Keep the experiment narrow and reversible. | Prove behavior in the live runtime. If simulator or screenshot tooling fails, pair with `apple-device-validation` and classify infrastructure before touching source. |
| A documented modifier compiles, but activation, focus, dismissal, or a first-party affordance does not behave as inferred. | Platform availability, SDK declaration, presentation binding, historical versus current documentation, first-party-only behavior, simulator limitations, hardware requirements, and actual runtime state. | Prefer the smallest explicit public-API binding or state fallback that completes the native contract. Keep the API only when it still provides value, and avoid recreating private system UI without a separate product justification. | Pair with `apple-device-validation`; exercise activation, cancellation or dismissal, navigation away and back, and physical-device behavior when required. Report a public-API limitation separately from an app defect. |
| A broad cleanup risks changing behavior or performance. | Existing tests, hot paths, telemetry, persistence, state projections, and public behavior. | Keep the correction narrow; extract tiny helpers and route performance-sensitive simplification to `apple-performance-cleanup`. | Run focused regression tests and comparable performance checks before claiming equivalence. |
| A macOS surface looks polished but is not release-ready. | Native window and control behavior separately from assets, signing, entitlements, packaging, and distribution state. | Correct UI semantics here; pair with `macos-productization` for icon, signing, packaging, notarization, and release claims. | Require both runtime UI evidence and the distribution-channel proof appropriate to the release. |

## Stateful Cross-Surface Audit

For pause/resume, begin/complete, active/inactive, connected/disconnected, or persisted-editing flows, trace all affected edges instead of patching the visible label:

- local and shared observable state;
- persistence and crash/relaunch restoration;
- timers, sensors, automated progression, and side effects;
- app lifecycle changes;
- widgets, Live Activities, notifications, exports, and App Intents;
- companion-device projections and connectivity messages;
- tests, previews, fixtures, and launch arguments.

The correction is incomplete if any edge can display or act on a different state from the primary control.

For a paused process, verify that progression controls, automated timers, projections, and companion behavior pause consistently; freezing only the visible clock is not a complete state transition.

## Exit Conditions

- The control uses the most appropriate platform semantic or documents why a custom reusable component is required.
- One state owner drives presentation and side effects.
- Foreground ownership is unambiguous: SwiftUI resolves button foreground, while a custom reusable button component may own only a compatible fill and shape contract.
- The workflow identifies one primary action without color carrying the hierarchy alone.
- Accessibility, localization, appearance, and compact-size behavior remain intact.
- Source tests and runtime evidence support the claims actually made; unresolved device or infrastructure limits are reported rather than hidden.
