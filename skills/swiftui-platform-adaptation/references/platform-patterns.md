# When a shared task fails on one destination

Use the same input, record and expected outcome when comparing implementations. A difference in presentation can be intentional. A different saved record or missing recovery path needs an explanation.

| Failure at the platform boundary | Discriminating check |
| --- | --- |
| An iPhone editor loses work only after interruption | Deny the dependent capability or interrupt the editor, then reopen. Check that the unaffected task still works and the intended draft policy survives. |
| A collapsed iPad sidebar changes the keyboard command target | Select A in one window and B in another. Resize A, activate its command by keyboard, and verify B stays untouched. |
| A watch shows an older edit than its companion | Disconnect, change the watch-local value and reconnect with delayed or duplicate deliveries. Verify the conflict outcome on both devices. Phone acknowledgement alone cannot establish the watch result. |
| A TV dialog loses its return target after a refresh | Open it by remote, remove its originating row, then dismiss. Pick a surviving neighbor or list control and verify directional focus can proceed. |
| A spatial task exits into the wrong scene | Enter from one of two windows, interrupt, resume and exit. Verify which window receives the result. Use hardware for comfort or physical reach claims. |

When a capability differs, exercise both the normal path and the defined fallback. Record each tested build destination, input, runtime and hardware-only observation.
