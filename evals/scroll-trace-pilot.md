# Scrolling trace pilot

Two independent readers reviewed the same [synthetic trace](fixtures/scroll-trace/TASK.md). Both kept the issue open. The pilot exercises interpretation of a performance handoff. The extracts contain no measurement of a real app, and one attempt per condition cannot establish a skill advantage.

## Method

Each reader received a fresh task directory and the request to respond to the developer as a colleague. The guided reader also received the full `apple-performance-cleanup` bundle generated by `scripts/skillctl.py bundle apple-performance-cleanup`. Both used separate fresh Codex sessions with the same inherited configuration, local file reads only, and no solution or reviewer rubric. Model snapshot and sampling settings were unavailable. A third reader received the task and anonymized answers A and B and evaluated the proposed decision, attribution, next change, and verification.

## A · baseline response

I’d keep the scrolling issue open. Moving thumbnail decoding to a worker lowered median main-thread CPU from 23% to 17%, but the hitch still lasts 39–42 ms across three repeats. The search index refresh happened at launch, and the worker finished decoding before the scroll began.

I’d trace which model changes each `PlaceRow` observes. During the 40 ms hitch, SwiftUI ran 312 row body updates for the same 24 visible IDs. Each update took under 1 ms, but main-thread samples span those updates. The sampled chain points to download progress triggering a library change. I’d test a change that lets the toolbar observe progress directly and each row observe only its title and saved flag.

I’d close the issue if repeated matched scrolls during active downloads show that progress updates no longer trigger row updates and frames consistently meet their presentation deadlines. I’d also verify that the toolbar still advances and that changing a saved flag updates the affected row.

## B · guided response

Keep the scrolling issue open. Median main-thread CPU fell from 23% to 17%, but the hitch still lasted 39–42 ms across all three runs in both builds. The search refresh finished at 410 ms and the recorded worker decode finished at 1800 ms, both before the 2240–2280 ms hitch. The trace gives us no per-row decode timings.

During the hitch, SwiftUI ran 312 `PlaceRow` body updates for the same 24 visible IDs. Each took under 1 ms, and main-thread samples were spread across them. The sampled cause chain points from download progress through the library model to a row. I’d test that link by having only the toolbar observe aggregate progress and each row observe its own title and saved flag.

I’d close the issue once repeated runs of the same gesture under the same conditions show the missed deadlines consistently disappear or the hitch materially shortens. Compare row-update counts over that interval to check the explanation. Separately, test that progress still advances in the toolbar and that changing a title or saved flag updates the correct row.
